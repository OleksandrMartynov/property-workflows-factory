## Research findings

- **Role constraint.** `profiles_role_check` was last set in `20261019174350_run_launch.sql:7-11` to `('manager','admin')`. The column default is `'manager'`. The convention is to drop the constraint, keep the default and re-add the constraint with the new set.
- **`private.launch_run`.** The latest definition is `20261025151836_template_versions.sql:318-406`, which reads tasks from the current template version and takes `for share` on the template. Two checks matter here:
  - The caller check at line 338 must stay `('manager','admin')`.
  - The assignee check at line 380 must become `('manager','admin','vendor')`.
- **`private.list_assignable_users`.** It is defined only at `20261019174350_run_launch.sql:273-285`, and it filters both the caller role and `p.role` to manager/admin.
  - The `public` wrapper selects only `id, email` and needs no change.
  - The new version only widens the `p.role` filter to include `vendor`. The caller filter stays `('manager','admin')`, so a vendor caller gets 0 rows.
- **`private.current_app_role()`.** It reads the role from `profiles` by `auth.uid()`, and the `profiles` select policy hides other users' rows from non-admins. The AC-VENDOR-02 test that checks a manager cannot read V's profile therefore needs no change.
- **Test helper.** `addUser(t, email, role)` in `tests/db/supabase-pglite.ts:107` creates a vendor, so it needs the new constraint to accept `'vendor'`.
- **Conformance rows.** `docs/conformance.md:103`, `:104` and `:111` currently read «відкладено (чекає реалізації)» with `—` in the code column.
- **Out of scope for this task** (later tasks in `design.md`): the vendor-only `run_tasks` policy, `complete_task`, `vendor_runs`, the UI, and `viewer.ts`.

## Design

One new migration, `supabase/migrations/20261109120000_vendor_role.sql`. Its timestamp is later than `20261027120752`, and no existing migration is edited. It does three things in this order:

1. **Role.** `alter table public.profiles drop constraint profiles_role_check;` then `add constraint profiles_role_check check (role in ('manager','admin','vendor'));`. The default stays untouched and no data changes.
2. **`private.launch_run`.** `create or replace` with the full body copied verbatim from the template_versions migration. The only edit is `p.role in ('manager','admin','vendor')` in the assignee validation. Keep `security definer`, `set search_path = ''`, `revoke … from public, anon` and `grant … to authenticated`.
   - A vendor caller hits `LAUNCH_NOT_ALLOWED` before any insert, so no run or `run_tasks` row is created.
   - Unassigned tasks still default to `v_uid`, the launching manager. That gives AC-VENDOR-01: V on tasks 3 and 4, A on tasks 1, 2 and 5.
3. **`private.list_assignable_users`.** `create or replace` with `p.role in ('manager','admin','vendor')` and the caller guard unchanged. Keep the same revoke and grant. I'd leave `public.list_assignable_users` alone, since it already returns only `id, email`.

Also update `docs/conformance.md` rows AC-VENDOR-01, 02 and 09. Set the status to «реалізовано», put the migration path in the code column, and keep the existing test paths.

## Risks

- **Dropped logic when copying `launch_run`.** The function has several guards: case-name trim and length, `for share`, `TEMPLATE_NOT_PUBLISHED`, `TEMPLATE_EMPTY`, and skipping assignee keys that aren't in the version. Dropping any of them would break the AC-RUN and AC-EDITOR tests. I'd copy the body wholesale and diff it against the old one.
- **Wrong source migration.** Copying from the older `20261021104639` file would lose version-based task copying. Use `20261025151836`.
- **`search_path`.** Every object reference in the new functions must stay schema-qualified because of `set search_path = ''`.
- **Existing data.** An existing `profiles_role_check` violation is impossible, because the new set is a superset.
- **Constraint name.** Dropping `profiles_role_check` assumes that is still the live name. The grep shows no other migration renamed it, but I didn't open the whole migration chain.
- **Hidden scenarios.** They may exercise vendor behaviour beyond these three ACs (`run_tasks` visibility, `complete_task`). Contract item 6 keeps those out of scope, so I don't plan to touch them.
- **Factory command policy.** Use only `node scripts/factory-tap.mjs` or `node node_modules/vitest/vitest.mjs run`, with no pipes or chaining.
