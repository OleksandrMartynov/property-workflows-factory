# Plan: assign a vendor and let the vendor work on their own tasks

## Research findings
- **Already done.** `20261109120000_vendor_role.sql` adds the `vendor` role and lets `launch_run` assign a vendor. It also lets `list_assignable_users` return vendors, and only a manager or admin can launch. This covers AC-VENDOR-01, 02 and 09.
- **RLS today.** `run_tasks_select_visible` was last changed in `20261021110918_rls_policies_require_auth_uid.sql`. It reads `auth.uid() is not null and private.can_see_run(run_id)`. `can_see_run` is true for admins, the run manager, or any assignee of a task in the run. A vendor therefore sees every task of a run they are assigned to.
- **`run_progress`.** It is a `security_invoker` view, so tightening the policy automatically narrows a vendor's counts.
- **`private.complete_task(uuid, boolean)`.** The latest definition is in `20261021093442_complete_task_confirmation.sql`. Three things block a vendor:
  - Line 22 only allows `manager` or `admin`, so a vendor gets NOT_ALLOWED even on their own task.
  - Line 34 grants access through `run_manager_id`.
  - The confirmation rule for the last required task, the run-completion logic and the idempotent repeat on `done` must all be kept.
  - `public.complete_task` is a thin wrapper, so it needs no change.
- **App.**
  - `viewer.ts` has `AppRole = "manager" | "admin"`, so `requireViewer` redirects a vendor to `/`.
  - `access.ts` (`canCompleteTask`) takes `AppRole`.
  - `page.tsx` always renders `RunDetail`, which shows emails, "Details", the run manager, the template and `run-progress`. It also calls `list_assignable_users`, which returns nothing for a vendor.
  - `completeTask` in `runs/actions.ts` already works for a vendor once `requireViewer` and the DB allow it.
  - `MarkDoneForm`, `groupBySection`, `requiredLabel`, `taskStatusLabel` and `StatusBadge` can be reused.
- **Red tests.**
  - DB tests: `tests/db/vendor-own-tasks-db.test.ts`, `vendor-complete-db.test.ts`, `vendor-complete-refused-db.test.ts`.
  - Unit and component tests: `tests/runs/vendor-role.test.ts`, `vendor-run-detail.test.tsx`, `progress.test.ts`.
  - E2E (UAT): `tests/e2e/vendor-tasks.spec.ts`.
- **Conformance.** Rows 04, 05 and 07 in `docs/conformance.md` are marked "відкладено" and need updating.
- **Scope.** AC-VENDOR-03, 06, 08 and 10 are not in this requirement. I only cover the `notFound()` behaviour in item (6) of the contract.

## Design
1. **One new migration**, `supabase/migrations/20261109130000_vendor_own_tasks.sql` (the timestamp must be later than `20261109120000`).
   - `alter policy run_tasks_select_visible ... using ((select auth.uid()) is not null and private.can_see_run(run_id) and ((select private.current_app_role()) <> 'vendor' or assignee_id = (select auth.uid())))`. Check that `current_app_role()` returns null-safe values.
   - `create or replace function private.complete_task(uuid, boolean)` is copied from the latest migration with the same signature, so no drop and the grants stay. Changes:
     - Allow `'vendor'` in the role check.
     - Right after locking the task and run, add `if v_role = 'vendor' then if v_task.assignee_id is distinct from v_uid then raise exception 'NOT_ALLOWED'; end if; else <existing manager/admin rule> end if;`.
     - Everything after that stays unchanged: the `done` idempotent return, `RUN_COMPLETED`, `CONFIRMATION_REQUIRED` and run completion.
     - Re-run `revoke ... from public, anon` and `grant ... to authenticated`.
2. **App role.**
   - `AppRole` gains `'vendor'`.
   - `ROLES` is updated and `isVendor(role)` is exported.
   - `canManageTemplates` stays admin-only.
   - Update the `requireViewer` comment.
   - `canCompleteTask` still type-checks. A vendor's `run_manager_id` can never equal their id, and the DB is the authority anyway.
3. **`formatVendorProgress(done, total)`** returns `Your tasks: ${done} of ${total} done`, placed next to `countProgress` in `progress.ts`.
4. **`vendor-run-detail.tsx`** exports `VendorRunDetail` with the props from the contract.
   - Group with `groupBySection`.
   - The section name is an `h2`.
   - Each row is a `<li data-testid="run-task">` with the name, `requiredLabel`, a `StatusBadge` using `taskStatusLabel`, and a `MarkDoneForm` while the status is `to_do`.
   - `needsConfirmation` is `task.id === lastRequiredTaskId`.
   - Show the `formatVendorProgress` line, computed from `countProgress(tasks)`.
   - Components come only from `@/components/ui` and colours from tokens.
   - No emails, "Details", manager, template, version or `run-progress`.
5. **`page.tsx`.** After `requireViewer`, if `isVendor(viewer.role)`:
   - Skip the `list_assignable_users` call.
   - Select only the task fields the vendor view needs.
   - If there are no tasks, call `notFound()`.
   - Otherwise render a `PageShell` with the case name and status, then `VendorRunDetail`.
   - Do not show the template name as the description.
   - Compute `lastRequiredTaskId` with `isLastRequiredTask`.
   - Managers and admins keep the existing path.
   - The `runs` select must not expose template fields to the vendor view.
6. **Docs.** Set rows 04, 05 and 07 to «реалізовано» and fill in the code paths: the new migration, `vendor-run-detail.tsx`, `viewer.ts`, `progress.ts` and `page.tsx`. Keep the test paths.

## Risks
- **Policy regression.** Narrowing the policy must not touch managers or admins. A user with a null role would fail the `<> 'vendor'` check, so confirm `current_app_role()` behaviour. Use `(select ...)` wrapping for performance, as the existing policies do.
- **`complete_task` drift.** The function must be copied from the latest migration, not an older one. Missing the confirmation, `RUN_COMPLETED` or idempotency logic would break the AC-TASK tests. Order matters: the vendor check goes before the general rule, and it must not fall through to the `run_manager_id` branch.
- **Last-required-task dialog for a vendor.** The vendor sees only their own tasks, so `isLastRequiredTask` over those rows can show a confirmation dialog when the task is not really the last. A truly last task is always flagged, so no case is missed. If the extra dialog is a problem, an alternative is a small security-definer helper that reports the whole-run state. That is out of scope for now.
- **Sibling policies.** `runs_select_visible` still lets a vendor read the run row, including `template_name` and `run_manager_id`. The page must not render them, but a direct API query would still return them. The contract only fixes `run_tasks`, so I'd flag this to the requirement owner rather than change it here.
- **Other `AppRole` consumers.** `layout.tsx` passes `role` to `AppShell`. The templates pages use `requireViewer` and `canManageTemplates`. `runs/page.tsx`, `proxy.ts` and the launch page also check roles. The list-for-vendor and templates-denied behaviour (AC-VENDOR-03, 08 and 10) is not specified here, so check that widening the type does not break them. Don't add new behaviour for them.
- **Hidden scenarios.** Likely cases are a vendor repeating a mark on a `done` task (idempotent, still allowed for their own task), a vendor marking a task in a completed run (`RUN_COMPLETED`), and a vendor with no tasks in the run (`notFound`). Keep the DB error mapping and `dbErrorCode` unchanged.
- **No test access to a DB.** I only read the code and ran nothing. The DB tests may need a local Supabase, so check how the allowed commands run them before relying on slices 1 and 2.
