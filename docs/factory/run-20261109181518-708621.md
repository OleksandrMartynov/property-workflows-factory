# Plan: assign a vendor and let the vendor work on their own tasks (AC-VENDOR-03, -06, -10)

## Research findings

**Already in place** (from the earlier vendor tasks, migrations `20261109120000` and `20261109130000`):
- `run_tasks_select_visible` already restricts a vendor to rows where they are the assignee.
- `private.complete_task` accepts a vendor on their own tasks.
- `VendorRunDetail`, `formatVendorProgress` (`src/lib/runs/progress.ts:14`) and `isVendor`/`requireViewer` exist.

**The gap:**
- `runs_select_visible` is `auth.uid() is not null and private.can_see_run(id)`, from `20261021110918`. `can_see_run` returns true for a vendor who has at least one task in the run. So a vendor can still read `runs` rows, including `template_name` and `template_version`, by sending a request directly.
- `src/app/(app)/runs/page.tsx` has no vendor branch. It reads `runs` and `run_progress` and renders the manager table, and it shows "Launch a template".
- The vendor branch of `src/app/(app)/runs/[id]/page.tsx:22-32` reads `runs` directly. Once the policy is tightened, `run` comes back null and the page shows "Run not found" even for the vendor's own runs.
- `src/app/(app)/page.tsx` (home) has no vendor handling. It reads `runs` and shows the agency counts.
- `docs/conformance.md` rows 105, 108 and 112 say «відкладено».
- Missing: `NO_VENDOR_TASKS`, `VendorRunsList`, `loadVendorRuns`, `loadVendorRun`, `vendor_runs` in `database.types.ts`, and the new migration.

**Conventions to follow** (`.factory/knowledge/conventions.md`):
- Helpers live in `private` (`security definer`, `set search_path = ''`) with a thin `security invoker` wrapper in `public`.
- The client type is `Awaited<ReturnType<typeof createClient>>`, as in `summaries.ts:4`.
- Use `@/components/ui` components and token colors only.
- Run tests only with `node scripts/factory-tap.mjs` or `node node_modules/vitest/vitest.mjs run`.

## Design

1. **One migration**, `supabase/migrations/20261109140000_vendor_runs.sql`. The timestamp is later than `20261109130000`.
   - `alter policy runs_select_visible on public.runs using (auth.uid() is not null and (select private.current_app_role()) is distinct from 'vendor' and private.can_see_run(id))`. I used the same pattern as the `run_tasks` policy. Managers and admins keep exactly their current access.
   - `private.vendor_runs(p_run_id uuid)`:
     - It returns `table(id uuid, case_name text, status text, created_at timestamptz, done integer, total integer)`.
     - It is `security definer` with `set search_path = ''`.
     - It reads the role from `public.profiles` by `auth.uid()`. If the caller is not a vendor, it returns no rows, so the function is not a way around the manager and admin policy.
     - It joins `runs` to `run_tasks where assignee_id = auth.uid()`, grouped by run.
     - `done` is `count(*) filter (where status = 'done')::integer` and `total` is `count(*)::integer`, both over the caller's tasks only.
     - It filters on `p_run_id is null or r.id = p_run_id` and orders by `created_at desc, id`.
   - `public.vendor_runs(p_run_id uuid)` is a `security invoker` SQL wrapper over `private.vendor_runs`.
   - Grants:
     - `revoke execute … from public, anon` on both functions.
     - `grant execute … to authenticated` on both functions.
     - Anon then gets permission denied.
   - `private.vendor_runs` needs `grant usage on schema private` for the wrapper to call it. I need to check how the existing wrappers (for example `complete_task`) handle this and copy that.
2. **Types:** add `vendor_runs` to `src/lib/supabase/database.types.ts`, so pages can pass the real client without casts. The `Args` are `{ p_run_id: string | null }`.
3. **Labels:** `export const NO_VENDOR_TASKS = "No tasks assigned to you yet."` in `src/lib/runs/labels.ts`.
4. **`VendorRunsList`** in `runs/_components/vendor-runs-list.tsx`:
   - Empty list renders `EmptyState` with `NO_VENDOR_TASKS`. No table, no link to `/templates`, no "Launch a template".
   - Otherwise each run is a list item with one `<Link href="/runs/{id}">` carrying the case name, a `StatusBadge` (`runStatusTone`/`runStatusLabel`), and `formatVendorProgress(done, total)`.
   - Nothing else is rendered. Look at `EmptyState`'s props before writing it, since `runs-list.tsx` uses `title`.
5. **Loaders:**
   - `loadVendorRuns(supabase)` makes exactly one `rpc('vendor_runs', { p_run_id: null })`, throws the error, and returns the rows as they are.
   - `loadVendorRun(supabase, runId)` makes `rpc('vendor_runs', { p_run_id: runId })`.
     - With 0 rows it returns `null` and does not read `run_tasks`. I'll check `tests/runs/vendor-run-loaders.test.ts:133-142` to see whether the test expects that.
     - Otherwise it reads `run_tasks` with `.eq('run_id', runId)` and the `VendorTaskRow` columns, ordered by `section_position` then `position`.
     - It returns `{ run: { id, case_name, status }, tasks }`.
6. **Pages:**
   - `runs/page.tsx`: call `requireViewer` first. For a vendor, `loadVendorRuns` and render `PageShell` with `VendorRunsList`, with no pagination, no `FilterBar` and no table.
   - `runs/[id]/page.tsx`:
     - The vendor branch uses `loadVendorRun` and calls `notFound()` on null.
     - It computes `lastRequired` from the loaded tasks and renders as it does now.
   - `(app)/page.tsx` (home): add the vendor redirect to `/runs`.
     - It currently uses `createClient` and `getClaims` directly, so the profile read needs to happen before the count queries.
     - The home page is the one place in the pages that needs a small restructure.
7. **Docs:** set rows AC-VENDOR-03, -06 and -10 in `docs/conformance.md` to «реалізовано». Fill the code-path column with the migration, `vendor-runs-list.tsx`, the two loaders and the pages. Keep the existing test paths.

## Risks

- **Policy regression for managers and admins.**
  - Changing `runs_select_visible` must not alter their access. The `is distinct from 'vendor'` form keeps the role check in the same style as the `run_tasks` policy.
  - A null role (a user without a profile) must behave as before.
  - Run the whole suite after slice 1.
- **`vendor_runs` as a data leak.**
  - Because it is `security definer`, it must scope strictly to `auth.uid()` and to the vendor role.
  - A manager or admin should get 0 rows, not other people's runs. I'll confirm in `tests/db/vendor-runs-db.test.ts` whether that is what it expects.
  - Anon must be denied.
- **Hidden dependencies on a vendor reading `runs`.**
  - `complete_task` is `security definer`, so it is fine.
  - Check any other vendor-reachable code that reads `runs`. The `MarkDoneForm` and `completeTask` action (`runs/actions.ts`) are the likeliest candidates. Revalidation or redirect code there may query `runs` and fail silently.
  - The home page also reads `runs`, but it is replaced by the redirect for vendors.
- **Home redirect ordering.** The profile read has to come before the count queries, or a vendor's counts query returns confusing values before the redirect.
- **Wrong count semantics.** `done` and `total` must count the caller's tasks only, not the whole run. A vendor in a run with other assignees must see "0 of 2", not the run total.
- **The `private` schema grants.** Mirror the existing wrapper pattern exactly. A wrong grant shows up as "permission denied for schema private" for authenticated users.
- **Not verified yet:** I haven't opened the visible tests. The details in the design that depend on them (the empty-run loader path, `EmptyState` props, the manager and admin behavior of the function) should be confirmed against them before writing code.
